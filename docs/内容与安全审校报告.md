## 🔴 必须改（3 条）

### R-1　同一张反馈卡内部自相矛盾：先说"不许降重继续"，下一条就让用户降重继续

**位置**：`app\plan.js:495–506`，`REACTIONS.compensation.lines`（第 1、2 条）

**原文**：
```js
lines: [
  '立刻停止当前动作。不是降重量继续，是先停。',
  '降到能完全控制重量的档位，重新看一遍动作示范。',
  '这个动作下次降级为热身辅助动作，不再作为主项。',
  '上斜方肌拉伸 + 肩胛下沉训练，列为每日必做。'
]
```

**为什么是问题**：
这是本次审校里最严重的一条。同一个反馈卡、第一句明确否定"降重量继续"，第二句立刻要求"降到能完全控制重量的档位"——用户读完只会执行后一句。学员左侧上斜方肌长期紧张、极易代偿，"降重量继续"恰恰是让代偿固化的做法。这不是文字瑕疵，是核心安全规则被自己拆掉。

对照 `app\goal.js:131` 也是同一问题（见 R-2）。另外第 3 条"这个动作下次降级为热身辅助动作"等于把已经触发代偿的动作留在训练里继续用，与"退出主项"的本意相反。

**建议改法**（把该卡 `lines` 整体替换为）：
```js
lines: [
  '立刻停止这个动作，今天不再做它。',
  '先别急着降重量继续——这一次就当没练。',
  '明天从空载或最轻一档重新开始，重新看一遍动作示范；连续两次都做干净了再考虑加回去。',
  '上斜方肌放松 + 肩胛下沉训练，列为每日必做。'
]
```
第 3 条"降级为热身辅助动作"删除；如确要保留观察，改成 `'这个动作在动作完全干净之前，不要放回主项，也不要再当热身辅助用。'`

### R-2　目标卡的阶段规则鼓励"带代偿信号降重继续"，与反馈页的停止指令冲突

**位置**：`app\goal.js:127–132`，`PHASES[0]`（适应期）`rules[3]`

**原文**：
```js
'一旦出现耸肩或身体歪斜，立刻降重到能控制为止'
```

**为什么是问题**：
这是用户会在"目标/阶段"页反复看到的一条硬规则，措辞是明确的行动指令——"降重到能控制为止"，意思是**继续做**。它与同一应用里的三处停止指令正面冲突：
- `app\plan.js:500`　`'立刻停止当前动作。不是降重量继续，是先停。'`
- `app\safety.js:269–270`　代偿 `action: 'STOP_THAT_LIFT'`
- `app\assess.js:178–184`　代偿 → `verdict: 'retreat'` 退回上一阶段

同一条规则在同一产品里给出两种相反的行动指导，属于典型的安全矛盾。

**建议改法**：
```js
'一旦出现耸肩或身体歪斜，立刻停下这个动作（不是降重量继续），去反馈页记一条；下一次从空载或最轻一档重新开始'
```

### R-3　白名单动作卡教用户在臀推机上架杠铃，与本项目"自由重量"红线正面冲突

**位置**：`app\data-exercises.js:555–576`，动作 `hip_glute_bridge_machine`（臀推机），字段 `setup`（第 570 行），关联 `crampRisk: "high"`（第 573 行）、`stopSignals[1]`（第 569 行）；对照 `app\safety.js:81–85` 自由重量红线、`app\data-machines.js:428`（杠铃深蹲架区 `status: "banned"`）、`app\data-machines.js:444`（自由重量哑铃区 `status: "banned"`）、`app\data-exercises.js:1127`（杠铃硬拉 `replaces`）

**原文**：
```js
"setup": "坐在垫子上，小腿垂直往上顶住靠垫，背部靠在滚垫上，杠铃（先用空杆或最轻）放在髋部沟槽里，双手抓杆稳住。"
"stopSignals": ["臀部突然抽筋或抽筋前兆，一有感觉立刻停", "杠铃压到胸口、肋骨被顶着不舒服", ...]
"crampRisk": "high",
```

**为什么是问题**：
三重冲突：

1. **与红线冲突**。本项目把"自由重量"列为绝对禁止类别，理由写得很清楚："新手无法自主纠正动作偏差，且无法配重，负荷不可控"（`safety.js:84`）。把杠铃架到髋部沟槽里，恰恰是这三项全中：需要现场配重、无人保护、负荷不可控。器材库还专门写了"这块区域别进……卸片时被砸"。
2. **与同一份数据自相矛盾**。`app\data-exercises.js:1127`（杠铃硬拉）写的是 `"改用臀推机或臀桥（自重），同样激活臀部且有靠垫支撑，不用扛杠"`——把臀推机定义为"不用扛杠"的替代动作；结果臀推机自己的 setup 让用户扛杠。
3. **与该动作自身的风险标记冲突**。这条动作 `crampRisk: "high"`，学员臀部极易抽筋，而"架杠铃 + 无人保护 + 抽筋前兆"是最糟糕的组合——抽筋时人无法自行卸杠。

**可达性说明（重要）**：`plan.js` 的 `fitScore()` 对该动作算出 `10 − 3(domsRisk mid) − 10(crampRisk high) = −3`，被 `.filter(x => x.s >= 0)` 排除，**当前不会出现在生成的计划里**。所以这是潜在风险，不是正在发生的线上风险。但文案留在数据层，只要评分权重或白名单一变就会出现在任务卡上，且它是白名单（未 `_banned`）动作，属于红线引擎放行、靠文案自己兜底——这种"引擎放行 + 文案说危险"的组合必须消除。

**建议改法**（`setup` 替换）：
```js
"setup": "坐在垫子上，小腿垂直往上顶住靠垫，背部靠在滚垫上。先做自重或器械自带的小配重片，双手扶住两侧把手稳住。不要自己往杠上加载荷——本项目的自由重量红线包含一切需要现场扛杠的架式负荷。"
```
同时把 `stopSignals[1]` 的 `"杠铃压到胸口、肋骨被顶着不舒服"` 改为 `"髋部垫子顶到肋骨或胸口不舒服"`。
另外 `app\data-machines.js:428` 的器材卡已把杠铃区标为 banned，建议在 `hip_thrust.statusNote` 里补一句："这台只用器械自带的小配重，不要自己加杠铃。"

### Y-1　抽筋话术：`safety.js` 里残留的"小口补水"与另外两处直接对撞

**位置**：`app\safety.js:255–260`，`SIGNAL_POLICY.cramp.reply`

**原文**：
```js
reply: '立刻停下放松该侧肌肉，慢慢屈伸关节，小口补水。当天训练到此结束，不补做。'
```

对照：
- `app\plan.js:479`　`'注意：「多喝水」不是有效解法。J Athl Train 2022 的循证综述明确把它列为无效的泛化建议。有效的是找出你的个体风险因素。'`
- `app\assess.js:171`　`'反复抽筋不是训练量问题。注意：多喝水不是解法（见 docs/参数依据核查报告.md）……'`
- `docs\参数依据核查报告.md:59`　R3 把 "drink more fluids" 明确列为**反面例子**

**为什么是问题**：
核查报告第三节写明"抽筋时「多喝水」……❌ 删除"，但这条结论只在 `plan.js` 和 `assess.js` 落地了，`safety.js` 的策略表里原封不动留着。同一份数据里对同一个问题给出正反两套答案，后续任何人以 `safety.js` 为准改代码或写新模块，都会把错的那句抄回去。

**可达性说明**：`app.js` 目前只调用 `Safety.markSafety()`（`app.js:40`），`SIGNAL_POLICY` / `respondTo()` 没有被渲染到界面，`README.md:120` 也明确写"改反馈话术 → `app\plan.js` 的 `REACTIONS`"。所以这条当前**不会出现在用户屏幕上**，属残留文案——但正因为它是"红线引擎的信号处理表"，留着比不留更危险。

**建议改法**：

```js
reply: '立刻停下放松该侧肌肉，慢慢屈伸关节，直到症状缓解。当天训练到此结束，不补做。注意：多喝水不是解法（见 docs/参数依据核查报告.md）。'
```

### Y-2　急性疼痛给出"今晚热敷"，属越界的自我处置建议，且时机可疑

**位置**：`app\plan.js:463–468`，`REACTIONS.pain.lines[2]`

**原文**：
```js
'今晚热敷疼痛部位，早点睡。',
```

**为什么是问题**：
本应用的边界是"只做训练安排"，不做处置建议（`app.js:86` 明确告诉用户"选「痛」会直接给你停止指令"）。但热敷属于典型的自我医疗处置；而且对**新发生**的疼痛，热敷并非默认处理方式——这条卡片处理的是"刚刚发生的痛"。应用没有能力区分是新伤还是旧伤，直接给一条处置指令，是在没有依据的情况下替用户做医疗决定（核查报告已多次因为"没有依据的泛化建议"撤回过话术）。

**建议改法**：
```js
'今晚这一课就到此为止，早点睡。疼痛部位先不要揉、不要自行热敷或上药。',
'明天观察：疼减轻了再从最轻重量开始；超过 3 天没好转，或伴随肿胀、关节响、动作受限，去看骨科或康复科。'
```
（第二条可与现有 `urgent` 文案合并，避免重复。）

### Y-3　痛后"换成纯轻有氧"与 `safety.js` 的"不换动作顶替"口径不一致

**位置**：`app\plan.js:467` 对照 `app\safety.js:252`

**原文**：
```js
// plan.js REACTIONS.pain
'今天剩下的任务取消，不补做。',
'明天这个部位不训练，换成纯轻有氧或休息。'

// safety.js SIGNAL_POLICY.pain
reply: '立刻停止该动作，不追加次数、不换动作顶替。今晚热敷，明天这一部位不训练。',
forbid: ['再坚持一下', '换个动作试试', '减重量继续']
```

**为什么是问题**：
两处讲的是同一件事（痛之后怎么办、明天怎么办），一处允许"换成轻有氧"，一处禁止"换动作顶替"。虽然指向的是次日、且部位不同，逻辑上不冲突，但同一产品对同一问题给出两种口径的原文，用户（以及后续维护者）无从判断哪条是准的。顺带一提，`safety.js` 那句里的"今晚热敷"与 Y-2 是同一个问题，改 Y-2 时应一并改。

**建议改法**：
把 `safety.js:252` 改为与 `plan.js` 同口径：
```js
reply: '立刻停止该动作，不追加次数、不换动作顶替。今天剩下的任务取消，不补做；明天这个部位不训练，做纯轻有氧或直接休息。',
```

### Y-4　代偿话术：`safety.js` 允许"换动作"，与 `plan.js` 的"先停"不同调

**位置**：`app\safety.js:267–272`，`SIGNAL_POLICY.compensation.reply`；对照 `app\plan.js:500–501`

**原文**：
```js
// safety.js
action: 'STOP_THAT_LIFT',
reply: '这是代偿信号，不是练到了。立刻降重或换动作，让出主导肌群。',
forbid: ['正常现象', '坚持一下就好了']

// plan.js
'立刻停止当前动作。不是降重量继续，是先停。',
'降到能完全控制重量的档位，重新看一遍动作示范。'
```

**为什么是问题**：
同样是未渲染的策略表，但它与 R-1 方向相反：这里说"换动作"，那里说"先停"。三处（safety.js / plan.js / assess.js）对代偿的处理各不相同：safety.js 换动作、plan.js 先停后降重、assess.js 退回阶段并自动降一档重量。代偿是本项目认定的"最重要的一类反馈"（`plan.js:505`），恰恰是口径最乱的一个。

**建议改法**：
```js
reply: '这是代偿信号，不是练到了。立刻停下这个动作，不要靠降重量继续完成；等动作做干净了再上。',
```
并把 `plan.js` 与 `assess.js` 的处理统一成同一句话（见 R-1 建议文案）。

### Y-5　四个阶段的规则里，只有强化期写了"痛/抽筋就停"，另外三段完全没提

**位置**：`app\goal.js:127–132`（适应期）、`143–148`（积累期）、`175–180`（巩固期）；仅 `160–164`（强化期）含 `"如果这 2 周出现腿重度酸痛或臀部抽筋，本阶段顺延，不硬推进"`

**为什么是问题**：

```js
'这一条任何阶段都一样：出现痛或抽筋，立刻停，不换动作顶替，不补做。'
```

### Y-8　承诺过度：目标卡把"8 周内改善 X"当成目标写死，情绪目标承诺"第一次就能感觉到"

**位置**：`app\goal.js:229`（`derive()` 的 `statement`）、`app\goal.js:80`（`PAINS[stress].why`）

**原文**：
```js
// goal.js:229
statement: `8 周内改善「${pain.label}」，每周 ${freq.days} 次、每次约 ${sess.minutes} 分钟的固定器械训练`,

// goal.js:80
why: '这个目标完全正当。运动对情绪的即时改善比增肌快得多，你第一次练完就能感觉到，不需要等 8 周。',
```

**为什么是问题**：
项目定位是"工具"不是"疗效承诺"。`statement` 是目标卡最显眼的一行，它把结果（8 周内改善高低肩/含胸驼背）写成了承诺句，而不是训练任务。肩高差是结构性差异，训练只能改善控制与代偿，不保证 8 周内可见变化；把不可控的结果承诺给用户，正是 `goal.js` 自己设 `FORBIDDEN` 想避免的事。`stress.why` 同样用"你第一次练完就能感觉到"做保证。

（同类、程度较轻：`goal.js:45`"静息心率比开始时低 5–10 次/分"、`goal.js:58`"肩和胸的轮廓开始有变化"——都是把预期结果写成了可达成指标。）

**建议改法**：
```js
// goal.js:229
statement: `用 8 周、每周 ${freq.days} 次固定器械训练，去试「${pain.label}」这件事能做到什么程度`,

// goal.js:80
why: '这个目标完全正当。运动对情绪的即时改善通常比增肌来得快，很多人第一次练完就有感觉；也有几次之后才感觉到的，都算正常。',
// goal.js:45 → '静息心率有没有比开始时低一点（5–10 次/分是常见范围，不保证）'
// goal.js:58 → '肩和胸的线条有没有开始变得清晰（照片对比，不称体重）'
```

### Y-9　承诺过度（承重风险）：器材卡用"几乎不会受伤""摔不了"做绝对化安全保证

**位置**：`app\data-machines.js` 五处 `dangerNote`

**原文**：
| 行 | 器械 | 原文 |
|---|---|---|
| 10 | 高位下拉器 | `拉不动就直接松手，几乎不会受伤。` |
| 26 | 坐姿划船机 | `拉不回来也不会闪到腰。` |
| 122 | 腿屈伸机 | `动作范围被限制，基本不会伤到。` |
| 170 | 髋外展机 | `有靠背、动作幅度很小，几乎没有受伤风险。` |
| 314 | 固定单车 | `摔不了` |

**为什么是问题**：
同一个项目的 `docs\参数依据核查报告.md` 刚刚因为"七折重量"这种编造数字撤回过话术，"几乎不会受伤"属于同一类——把风险说没，且没有任何依据。这几条会直接降低学员对器械风险的预判（尤其 314 的"摔不了"，在把手上坐姿后仰是真实存在的）。同类还有 `app\data-exercises.js:989`（哑铃推举 `replaces`）`'肩峰撞击和斜方肌代偿都为零'`、`app\data-machines.js:236`（臀推机）`'练屁股最有效的一台'`、`app\data-machines.js:540`（龙门架）`'路线固定、不用担心代偿'`——都是零风险/最优解式的绝对表述。

**建议改法**（统一口径：说清**为什么**风险低，而不是说"没有风险"）：
```js
// 高位下拉器
'全程有垫子卡住腿，绳子有重量上限，拉不动就直接松手。风险低，但坐姿没调好、腿没压实一样会伤。'
// 坐姿划船机
'胸口有垫子顶住，动作幅度被限死，比站姿划船安全；腰还是要跟着髋走，不要靠弓背甩。'
// 腿屈伸机
'坐姿有靠背、腿被膝垫压住，动作范围被限制；踢到接近伸直就停，锁死膝关节仍然是风险。'
// 髋外开/外展机
'有靠背、动作幅度很小，风险低；幅度开太大身体会后仰借力。'
// 固定单车
'坐着踩，脚下有固定踏板，摔倒风险低；鞍座调太低反而会伤膝盖。'
// data-exercises.js:989
'改用推胸机（中立握），把肩的负荷换成胸的负荷，肩膀全程有靠背托着，肩峰撞击和斜方肌代偿的风险显著降低'
// data-machines.js:236
'推荐给你用：练臀很有针对性，而且有靠有垫，比徒手臀桥稳。'
// data-machines.js:540
'想练背直接去「高位下拉器」，路线固定、代偿风险小得多。'
```

## 🟢 可选优化（5 条）

### G-1　"治高低肩专用"用了"治"字

**位置**：`app\data-exercises.js:901`，动作名 `绳索肩胛后缩（治高低肩专用）`

**为什么是问题**：应用只做训练安排，不做治疗；"治"是疗效宣称，也是全库唯一的诊断性措辞。同条 `searchHint` 里的"矫正"是对外搜索词，不展示给用户，可保留。

**建议改法**：`'绳索肩胛后缩（针对左右肩高低的纠正练习）'`（动作名同时会出现在 `fitScore` 的 `肩胛` 加分判断里，`/肩胛/.test(ex.name)` 仍命中，改名不影响逻辑。）

### G-2　"排除缺钙、缺镁、循环问题"列举了具体病名

**位置**：`app\plan.js:482`，`REACTIONS.cramp.urgent`

### G-3　动作名暗示单腿，与项目"禁单侧"原则表面冲突

**位置**：`app\data-exercises.js:371–392`，动作 `standing_leg_curl`，`name: "腿屈曲（站姿单腿弯曲机）"`，但 `symmetric: true`、`setup: "两只脚同时挂住，左右都要做"`

**为什么是问题**：红线引擎靠 `symmetric === false` 拦单侧动作（`safety.js:130`），这条标了 `true`，因此不会被拦；但名字里的"单腿"与项目表面原则相反，用户在搜索/图鉴里看到会以为这是被禁的那一类。目前该动作 `fitScore = 2`，在腿日排不满时**可能**被排进计划。

**建议改法**：把 `name` 改为 `'腿屈曲（站姿双腿机）'`，并在 `setup` 里补 `'这台是双腿一起做的，不是单腿动作；单腿箭步蹲那类是禁的。'`

### G-4　`volumeFor()` 的 `rpe` 字段写成了描述句，最后一档语义不通

**位置**：`app\plan.js:152–171`，`volumeFor()`

**原文**：
```js
case 'strengthen': return { sets: 4, reps: 10, rpe: '接近但不超过 10 次', ... };
default:            return { sets: 4, reps: 10, rpe: '全程动作不变形', ... };
```

**为什么是问题**：`rpe` 是与 `sets`/`reps` 并列、会被渲染到任务卡上的字段。前三阶段写的是"还能再做 N 次"（RPE 语义正确），后两阶段换成了动作描述，`接近但不超过 10 次` 与 `reps: 10` 重复且表述矛盾（都做满 10 次了还"不超过 10 次"），用户会看不懂这一课到底要练到哪。

**建议改法**：`rpe: '一组下来还能再做 2–3 次就停'`、`default` 分支改 `rpe: '全程动作不变形，次数做不满也不硬撑'`。

### G-5　证据登记表把"个人伤史"放进了 A 级"有循证支持"

**位置**：`app\evidence.js:26–31`（条目 1）与 `app\evidence.js:19`（`LEVELS.A.desc`）

**原文**：
```js
A: { key: 'A', label: '有循证支持', cls: 'ok', desc: '来自系统综述或 meta 分析，可自行复核' },
...
{ param: '高位下拉 ≤ 5kg，必须双手对称', level: 'A',
  why: '来自你的个人伤史：曾因单臂高位下拉 20kg 导致左斜方肌严重代偿酸痛。',
```

**为什么是问题**：这条本身写得很坦白（source 已注明"非通用文献"），但它被放进 A 级，而 A 级的说明承诺"来自系统综述或 meta 分析，可自行复核"——用户按分类去数"有循证支持（N 条）"时会被多算一条。

## 附带发现（不属于四类检查，但影响"用户实际看到哪句话"）

### F-1　`fitScore` 的优先白名单 23 条里只有 13 条能精确命中，纠正类动作排不上计划

**位置**：`app\plan.js:47–54`（`PRIORITY` 数组）与 `app\plan.js:55`（`const idx = PRIORITY.indexOf(ex.name)`）

**为什么是问题**：
`indexOf` 是精确字符串匹配，而数据里的动作名带括号后缀。以下 10 条永远匹配不上：
`'坐姿划船'`（实际名 `坐姿绳索划船（双手同时）`）、`'胸部支撑划船'`（`胸部支撑划船（俯卧靠垫）`）、`'绳索肩胛后缩'`（`绳索肩胛后缩（治高低肩专用）`）、`'推胸机'`（`推胸机（中立握）`）、`'髋外展'`（`髋外展机`）、`'坐姿腿屈曲'`（`坐姿腿弯举`）、`'髋内收'`（`髋内收机`）、`'提踵'`（`站姿提踵机` / `坐姿提踵机`）、`'跑步机'`（`跑步机快走`）、`'肩后束（反飞鸟）'`（`器械反飞鸟（后束，双手同步）`）、`'直臂后伸'`（`直臂后伸（双手同步低位绳索）`）。

连带后果：白名单里两条纠正动作 `绳索肩胛后缩`（名字直接写着"治高低肩专用"）和 `器械反飞鸟` 的 `bodyPart` 都是"肩"→映射到 `chest` 槽位，得分只有 10，而同槽位的 `上斜推胸机` 得 53，**这两条最贴合影员特殊情况的动作在计划里基本排不上**；用户看到"治高低肩专用"这句话的机会接近于零。这属于内容有效性缺陷，建议改成前缀/包含匹配（`PRIORITY.some(p => ex.name.startsWith(p))`）。
