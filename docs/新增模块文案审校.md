### W-1　周包第 6 周把"降重继续"写成重量规则，并把降重列为本周成就奖励

**位置**：`app\weekpack.js:149`（`week` 6 的 `goal`）、`app\weekpack.js:151`（`loadRule`）、`app\weekpack.js:152`（`milestone`）

**原文**：
```js
goal: '把加过的那几台重新做干净；动作一变形就主动降回去。',
loadRule: '加过的那几台重新做干净。高位下拉还是 5 kg。动作一变形就降回去。',
milestone: '有一次在动作变形的时候主动把重量降回来，就算数 —— 这就是这周真正的收获。',
```

**为什么是问题**：
三重问题叠在一起：

1. **与 `plan.js` 的核心安全规则正面冲突**。`plan.js:504–505` 写得很死：
   ```
   '立刻停止这个动作。这一次就到这里，不要降重量接着做。',
   '降重量继续 = 负荷还是被同一块代偿肌接管，只是数字变小了，代偿会固化。',
   ```
   而这里给的是「动作一变形就降回去」——一条**明确的降重继续指令**，且被放在 `loadRule`（"这周重量"）这个位置，用户会把它当成规则执行。

2. **同一文件内部自相矛盾**。`weekpack.js:103`（第 2 周 `focus`）刚刚写过正确版本：
   ```
   '出现耸肩或歪斜就停下这个动作（不是降重量继续），去反馈页记一条，下次从空载或最轻一档重新开始。'
   ```
   第 2 周说"不是降重量继续"，第 6 周说"变形就降回去"。同一个文件、同一个信号、两种相反指令。

3. **`milestone` 把它变成奖励**。这是本轮最重的一处：它不只是指令降重，而是把"降回来"定义成本周**做到就算数**的成就。上一轮报告 R-2 的问题是"指令错了"，这一条更进一步——**奖励错了**。对一个把"做 0 项也算完成"当原则的产品，把"降重继续"包装成"这周真正的收获"，等于告诉用户这是正确做法。

**背景**：这不是 `weekpack.js` 作者凭空发明的，是继承了 `goal.js:195`（`PHASES[2].exitCondition = '愿意在动作不干净的时候主动降重量——这本身就是达标'`）和 `assess.js:63`（`text: '在动作不干净时主动降重量，而不是硬扛'`）。也就是说现在有 **`goal.js` + `assess.js` + `weekpack.js` 三处说"降重"，`plan.js` + `safety.js` 两处说"停"**。上一轮报告 R-2 只改了 `goal.js` 的 `rules[3]`，没动 `exitCondition`，所以新模块抄的是没改的那一份。

**建议改法**：
```js
// weekpack.js:149
goal: '把加过的那几台重新做干净；动作一变形就停掉那台，不要降重量接着做。',
// weekpack.js:151
loadRule: '加过的那几台重新做干净。高位下拉还是 5 kg。动作一变形就停下这个动作，本次不再做它。',
// weekpack.js:152
milestone: '有一次在动作变形的时候主动停掉那台机器、没有硬做完，就算数 —— 这就是这周真正的收获。',
```
同时建议把 `goal.js:195` 的 `exitCondition` 与 `assess.js:63` 的 `text` 一并改成同一句（不在本任务写范围内，但 W-1 不连带改这两处就不算修完）。

### P-1　本周完成度卡顶部做倒计时，与"做 0 项也算完成"直接对立

**位置**：`app\progress.js:213`（`daysLeft` 计算）、`app\progress.js:260`（渲染）

**原文**：
```js
// :213
const daysLeft = 7 - w.index;
// :260
meta.push('本周还剩 ' + p.daysLeft + ' 天');
```

**为什么是问题**：
这是本次审校里唯一一条**纯粹的施压表述**，而且它出自一个把"不施压"写成硬约束的文件。

1. **它是倒计时**。`w.index` 是本周已过的天数（周一=0），所以周一打开显示「本周还剩 7 天」，周日打开显示「本周还剩 1 天」。一周刚开始就先说"还剩"，周末逼近时变成催办。这正是 `progress.js:5` 自己批评的 Keep 那套"还差 31 千卡"的紧迫感的同型结构。
2. **它与进度无关**。`meta` 的 push 是无条件的，`done >= expected`（`tone === 'settled'`）时进度条被 CSS 隐藏（`:71`），但「本周还剩 N 天」照常显示。用户已经练够了，卡片还在给他倒计时。
3. **它与本文件头声明冲突**。`progress.js:9` 写：「永远不说"未达标""没完成""欠""差""失败"，没有百分比告警，没有红色。」禁用词扫描当然扫不出「还剩 N 天」——这正是本任务要求"独立复核、不信任自述"的原因：**文件自己立的护栏是词表级的，漏掉了语义级的压力**。

**建议改法**：
```js
// :260 —— 删掉这一行，或换成不产生缺口感的表述
if (p.expected && !p.settled) meta.push('这周你想练 ' + p.expected + ' 次，哪天来都行');
```
若产品上确实需要"这周还有几天"的信息，应改成中性事实（如「今天是周 X」），不要用「还剩」。

### P-2　"达标"的阈值在三个模块里是三个不同的数，且同屏显示

**位置**：`app\progress.js:194`（`expected`）对照 `app\goal.js:267`（`minPass`）、`app\plan.js:322`（`minPass`）

**原文**：
```js
// progress.js:194 —— 把 freq.days 直接当达标线
const expected = (st.goal && st.goal.freq && Number(st.goal.freq.days)) || 0;

// goal.js:267 —— 达标线是 freq.days - 1
minPass: '每周至少出勤 ' + Math.max(1, freq.days - 1) + ' 次就算达标（不是 ' + freq.days + ' 次）',

// plan.js:322 —— 达标线是"2 个任务"，单位都不一样
minPass: `完成 ${Math.min(2, tasks.length)} 个任务就算达标。今天做 0 个也可以。`
```

**为什么是问题**：
用户定「每周 3 次」时，同一个应用给出三个互不相同的"达标"：

| 模块 | 达标线 | 单位 | 出现位置 |
|---|---|---|---|
| `goal.js` | 2 次/周 | 出勤次数 | 目标页「及格线」 |
| `progress.js` | 3 次/周 | 出勤次数 | 计划页顶部完成度卡 |
| `plan.js` | 2 个任务/课 | 动作任务 | 每张训练日卡片底部 |

后果是具体的：用户按 `goal.js` 的"2 次就达标"练到 2 次，切到计划页看到的是「这周已经练了 2 次，这就算数」（`tone: good`，**未 settled**），进度条显示 2/3，还有一条"剩下的 1 次不用赶"。同一屏上，一个说够了、一个说 2/3。用户无从判断哪个是准的。

而且这三个模块**说的是同一个词**——「达标」/「就算数」/「算完成」。口径不一致之外还叠加了用词不一致（见 Y-4）。

**建议改法**：
统一到一个数。建议以 `goal.js` 的 `freq.days - 1` 为准（它是刻意压低的及格线，符合本项目定位），`progress.js` 改为：
```js
// :194
const target = Number(st.goal.freq.days) || 0;
const expected = target > 0 ? Math.max(1, target - 1) : 0;   // 与 Goal.derive().minPass 同源
```
并在 `progress.js` 的 `detail` 里说明「你自己定的目标」与「及格线」的关系。`plan.js:322` 的任务级 minPass 建议改成不与周目标比大小的表述（如「今天做 1 个就算完成，做 0 个也可以」）。

### W-2　周包的"没做到就停在这周继续"把进步变成了门槛

**位置**：`app\weekpack.js:106`（`week` 2 `note`）、`app\weekpack.js:128`（`week` 4 `note`）

**原文**：
```js
// :106
note: '这是适应期的最后一周。做到上面那条就可以进下一阶段；没做到就停在这周继续，不赶时间。'
// :128
note: '这是积累期的最后一周。做到了就可以考虑小幅加重量，做不到就继续练这周的内容。'
```

**为什么是问题**：
句式是「做到 A 就可以进下一阶段；没做到就停在这周」。虽然末尾补了"不赶时间"，但**主句建立的是条件式晋升**：用户被明确告知存在一个"没做到"的状态，而且这个状态有后果（停滞）。

1. **与产品原则冲突**。`docs\内容与安全审校报告.md` 记录的产品原则是"不把训练当硬性 KPI""做 0 项也算完成"。这里把"连续 2 次无耸肩无歪斜"设成进下一阶段的门槛，并显式命名了失败分支。用户在第一次训练后就会开始算"我还差几次干净记录"。
2. **与同一文件的 footer 自相矛盾**。`weekpack.js:466–467` 写：「练几次、做几项都行，做 0 项也算完成 —— 包不会因为少练一次就作废。」而 :106 说没做到就停在这周。
3. **与 `assess.js` 的立场冲突**。`assess.js:10–12` 明确写「这里只做『建议』，不做强制……强制自动降级会在误报时伤害积极性」。周包这里用的是比"建议"更强的口吻（"就可以进 / 就停在这周"）。
4. **"停在这周继续"本身是个惩罚性措辞**。"继续"在语境里等于"你还没通过"。对比 `plan.js:529`（`low` 信号）的「计划往后顺延，不补课」——那个措辞是解脱，这个措辞是留级。

**建议改法**：
```js
// :106
note: '这是适应期的最后一周。这一条是给你自己看的参考，不是门槛 —— 做到就自然往下走，没到就多待几天，两种都不影响后面。'
// :128
note: '这是积累期的最后一周。想加重量的话，先看看这一条；不想加就先按现在的重量练，一样算数。'
```

### C-1　代偿仪表给的是"退回最轻一档再做熟"，漏掉了"先停"这一步

**位置**：`app\compensation.js:293`（中等代偿分支）、`app\compensation.js:307–308`（偏多代偿分支）

**原文**：
```js
// :293
'想知道具体是哪个动作，去「反馈」页的记录里对一下，把那个动作退回最轻一档再做熟。'
// :307-308
'现在可以做的事只有一件：把触发代偿的那个动作退回最轻一档，先把动作做熟，重量以后再说。'
```

**为什么是问题**：
`compensation.js` 是本项目里最直接讲代偿的地方（它整张卡就是代偿统计），但它的处置建议只覆盖了"下一次怎么办"，**没有覆盖"这一次怎么办"**。

1. **缺了停止指令**。`plan.js:504` 的第一句是「立刻停止这个动作。这一次就到这里，不要降重量接着做。」`compensation.js` 的两个分支都直接跳到"退回最轻一档再做熟"，读者会理解成"降轻一点继续做"——这正是 `plan.js:505` 判定为会让代偿固化的做法。
2. **它是用户主动来看的卡片**。`plan.js` 的 REACTIONS 要用户切到反馈页点一下才看到；`compensation.js` 直接挂在计划页（`app.js:554`），是**更早、更容易被读到**的那一份。也就是说，代偿发生时用户最可能先看到的是这张卡。
3. **"再做熟"隐含继续使用**。`plan.js:507` 明确要求「这个动作在完全做干净之前，不要放回主项，也不要当热身辅助用」，而这里说"再做熟"，方向相反。

**建议改法**（两个分支都补第一句，与 `plan.js` 同口径）：
```js
// :293
'想知道具体是哪个动作，去「反馈」页的记录里对一下。那个动作这一次就先停掉，' +
'下次从空载或最轻一档重新开始，做熟为止。',
// :307-308
'现在可以做的事只有一件：把触发代偿的那个动作先停掉，下次从空载或最轻一档重新开始，' +
'先把动作做熟，重量以后再说。'
```

### W-3　`weekpack.js` 的 `audit()` 覆盖不足，实测 `ok: true` 却漏掉真实问题

**位置**：`app\weekpack.js:360`（`BANNED_WORDS`）、`app\weekpack.js:392`（`FIELDS`）、`app\weekpack.js:362–411`（`audit()`）

**原文**：
```js
// :360
const BANNED_WORDS = ['未达标', '失败', '落后', '欠', '必须完成'];
// :392
const FIELDS = ['goal', 'focus', 'loadRule', 'milestone', 'note'];
```

**实测结果**（在 `node` 下直接 `require('./app/weekpack.js').audit()`）：
```json
{ "ok": true, "problems": [], "phases": 4, "packs": 8, "fromGoal": false }
```

**为什么是问题**：
`ok: true`，但同一个文件里实际存在本报告 W-1（「动作一变形就降回去」）和 W-2（「没做到就停在这周继续」）两条 🔴。`audit()` 一条都没报。具体漏在哪：

1. **词表太窄**。只拦 5 个词。`goal.js:153` 的「必须」、`progress.js:260` 的「还剩 N 天」、W-2 的「没做到 / 做不到」、`plan.js:322` 与 `goal.js:267` 的「达标」都不在表里。特别是「达标」——项目里同时存在「就算达标」和「未达标」被禁，等于只禁了否定式，放过了肯定式。
2. **只扫 5 个字段**。`FIELDS` 是 `goal/focus/loadRule/milestone/note`，**不扫渲染层的固定文案**——而 `:452`（`'8 周安排 · 每周一个小包'`）、`:456–458`（meta）、`:465–467`（footer）是每次打开都会显示的，用户看到它们的次数比 `focus` 多得多。
3. **不扫拼接结果**。`forWeek()` 拼出的 `packName`（`:326`）、`phaseWeeks`（`:323`）不经过扫描；`phaseName` / `phaseHeadline` 来自 `Goal.PHASES`，也不扫。所以 `goal.js` 里的话术问题不会被这个 audit 发现。
4. **它检查的是"关键词"，不是"语义"**。W-2 的核心问题是**条件式晋升的句式**，用任何词表都扫不出来。

**建议改法**（不是让它更严，而是**不要把它当通过依据**）：
- 至少把 `BANNED_WORDS` 扩到含「必须」「应该」「没做到」「做不到」「达标」「还剩」「坚持」「打卡」。
- `FIELDS` 之外增加一个 `RENDER_TEXT` 常量数组，把渲染层的固定文案收进去一起扫。
- 在 `audit()` 返回里加一个 `covers` 字段，写明"本次只扫了关键词与指定字段，语义级压力不在覆盖范围"，避免下一个人看到 `ok: true` 就认为审校通过。
- 在文件头 `:63`（`audit() 里带禁用词扫描，改文案时它会拦住你`）后补一句限制说明。

### C-2　「干净」一词在 `compensation.js` 与 `assess.js` 里是两个定义

**位置**：`app\compensation.js:331`（`streak`）、`app\compensation.js:221`（`streakLine` 输出）、`app\compensation.js:373`（`label`）；对照 `app\assess.js:138–140`（`cleanStreak`）

**原文**：
```js
// compensation.js:331 —— "干净" = 没有代偿
const streak = countBack(chrono, function (e) { return !e.compensation; });
// compensation.js:221 —— 输出给用户看
if (compensation > 0 && streak >= 3) return '最近连续 ' + streak + ' 次是干净的。';
// compensation.js:373
label: total === 0 ? '还没有记录' : (clean + ' / ' + total + ' 次干净'),

// assess.js:138-140 —— "干净" = 痛、抽筋、代偿三类全无
for (let i = recent.length - 1; i >= 0; i--) {
  const e = recent[i];
  if (!e.pain && !e.cramp && !e.compensation) cleanStreak++;
```

**为什么是问题**：
`compensation.js` 自己在 `:28` 的注释里承认了这个差异（"这与 assess.js 的 cleanStreak 口径不同"），但它**只提供了 `cleanStreak` 字段备用，没改用户看到的文案**。用户看到的是「最近连续 N 次是干净的」——这句话里"干净"排除了代偿，**不排除疼痛和抽筋**。而同一产品的反馈页（`assess.js` 驱动的「我现在的状态」卡）用同一个词表示三类全无。

具体后果：用户有一次抽筋、三次无代偿，`compensation.js` 会说「最近连续 3 次是干净的」，`assess.js` 的 `cleanStreak` 是 0。两个数字都叫"干净"，一屏之隔（计划页 vs 反馈页）。

**建议改法**：
不要在用户文案里用裸的「干净」。`compensation.js:221` 改为：
```js
if (compensation > 0 && streak >= 3) return '最近连续 ' + streak + ' 次没有报代偿。';
```
`:373` 的 `label` 改为 `(clean + ' / ' + total + ' 次没有代偿')`。`clean` 变量本身也建议重命名为 `noCompensation`，避免下一个读代码的人沿用错误定义。

### P-3　`done === 0` 时说"这周还没开始"，对第一天打开的新手是负面框架

**位置**：`app\progress.js:156–163`

**原文**：
```js
if (done === 0) {
  return {
    tone: 'neutral',
    headline: '这周还没开始 —— 哪天来都行，今天来也算',
    detail: '你给自己定的是每周 ' + expected + ' 次。' +
```

**位置**：`app\progress.js:167–174`

**原文**：

需要提的是文件结构：`audit()` 的 `msg`/`fix` 是写给开发者看的（含"违反 WCAG 1.4.4"这类术语），和 `:356` 这类真会播报的文案同处一个文件。目前 `app.js` 没有调用 `UX.audit()`，所以不会渲染到界面；但后续若有人把审计结果做成界面（这在无障碍工具里很常见），这些术语会直接呈现给用户。

**建议改法**：在 `ux.js` 的 `announce` / `alert` 定义处（`:223`、`:229`）加一行注释，写明"这两个函数的参数是唯一会到达用户的文案；`audit()` 的 msg/fix 只面向开发者"，给后续维护者划清边界。

## 附带发现（不属于五类检查，但影响"用户看到哪句话"）

### F-1　`progress.js` 承诺了一个界面上不存在的操作路径

**位置**：`app\progress.js:161`（"练 0 项也完全没有问题"）、`app\progress.js:299`（"做 0 项也记 1 次出勤"）；对照 `app\app.js:682–693`

`progress.js` 的口径是 `done = 本周 sessions 条数`，而 `sessions` 只有一条写入路径：`app.js:687` 的 `Log.logSession(...)`，触发条件是训练日卡片的 checkbox `change` 事件（`:686`）。也就是说，**用户必须主动勾"练完勾一下"才会产生一条出勤记录**。

但 `progress.js:299` 对用户说的是「做 0 项也记 1 次出勤」。新手第一天什么都没练、也没有理由去勾"练完"，`done` 就是 0，看到的是「这周还没开始」（P-3）。**文案承诺的"做 0 项也算"，在界面上没有对应的入口。**

另外 `app.js:687–688` 的实现是：取消勾选时也会再执行一次 `logSession`（`toast('已取消')` 但记录已写入），所以 `done` 会随勾选/取消反复累加。这会直接放大 P-1 和 P-2 的观感问题（数字虚高、达标判定失真）。这条属于代码缺陷，不在本次审校范围，但建议与 P-2 一起处理。

### F-2　反馈页的「出勤率 N%」与 `progress.js` 的措辞护栏冲突

**位置**：`app\app.js:929`（`'出勤率 ' + a.rate + '%'`）、`app\app.js:921`（`Log.attendance`）；对照 `app\progress.js:9`

`progress.js:9` 声明「没有百分比告警」。但反馈页的训练记录卡上有一个 `Log.attendance()` 算出的「出勤率 N%」（`log.js:193–205`，按 `createdAt` 推算周数 × `freq.days`）。这个百分比与 `progress.js` 的 `done/expected` 分子分母都不同，会出现"完成度卡说 2/3，记录卡说出勤率 67%"这类同屏矛盾。

`docs\ux-integration.md:285–297` 已经记录过"三处本周口径不一致"，但那是**时间窗**层面的（已由 `Log.weekStart()` 统一）。这里是**统计口径**层面的（次数 vs 百分比、自然周 vs 自创建以来），尚未统一。建议在下一轮处理。
